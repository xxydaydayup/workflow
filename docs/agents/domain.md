# 领域文档

说明工程技能在探索本仓库代码时，如何使用领域文档。

## 开始探索前，先阅读相关文档

- 仓库根目录的 `GLOSSARY.md`；或者
- 如果根目录存在 `GLOSSARY-MAP.md`，则按其中的指引阅读与当前主题相关的上下文词汇表
- `docs/adr/` 中涉及当前工作区域的架构决策记录。多上下文仓库还应检查 `src/<上下文>/docs/adr/` 中的上下文级决策

讨论审批流业务语义、模型或实现时，还要阅读 [立项申请 BPMN 业务基准](../examples/立项申请.bpmn)。以它作为一种具体流程行为：审批结论可以决定条件分支；会签节点的完成规则与通过/不通过结论分开理解；驳回按图上目标节点继续，示例中回到申请单，重新提交后重新经过后续审核。该示例不限定所有流程必须回到申请人。保留业务基准中尚未说明的规则为待确认事项，不从 BPMN 技术配置推断业务含义。

如果这些文件不存在，请直接继续工作，不必特别指出，也不要提前建议创建。`/domain-modeling` 技能（由 `/grill-with-docs` 和 `/improve-codebase-architecture` 调用）会在领域术语或决策实际明确后按需创建这些文件。

## 文件结构

单上下文仓库（适用于大多数仓库）：

```text
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-示例决策.md
│   └── 0002-示例决策.md
└── src/
```

多上下文仓库（根目录存在 `GLOSSARY-MAP.md`）：

```text
/
├── GLOSSARY-MAP.md
├── docs/adr/                    ← 系统级决策
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/            ← 上下文级决策
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## 使用词汇表中的术语

在 issue 标题、重构提案、假设或测试名称等输出中提到领域概念时，请使用 `GLOSSARY.md` 定义的术语。不要改用词汇表明确避免的同义词。

如果需要的概念尚未收录，这可能意味着项目并未使用你准备引入的术语，也可能说明词汇表确实存在缺项；请重新检查术语，或将缺项记录下来，留待 `/domain-modeling` 处理。

## 指出与架构决策的冲突

如果输出与现有架构决策记录冲突，请明确指出，不要默默覆盖。例如：

> _这与 ADR-0007（事件溯源订单）冲突，但有必要重新讨论，因为……_
