# 0001 - 引入业务模型层，编译下沉后端

官方 BPMN 设计器（bpmn-js）对业务管理员不友好；换用 react-flow 重画后仍未解决，因为不友好的根源在概念层——BPMN 术语（排他网关、assignee、formKey、监听器类名）和手写 EL 表达式直接暴露给用户——而非渲染层。决定：前端唯一编辑对象是与 BPMN 解耦的**业务模型**（由枚举化的审批模式组成）；业务模型到流程定义的编译在后端完成；监听器、formKey 等技术配置从设计界面消失，下沉为模板级预置。

## Considered Options

- 在现有 BPMN JSON 模型上继续加中文皮肤：被拒。适配层退化为格式转换，表达式与变量名仍需用户手工对齐。
- 前端编译（前端生成 BPMN XML）：被拒。业务模型 schema 演进会被 XML 兼容性锁死，camunda 命名空间知识泄漏进前端。

## Consequences

- 表达力收缩为枚举化的审批模式，Camunda 全量能力不再对业务管理员开放。
- 后端新增"业务模型 → 流程定义"的编译职责；现有 json2xml 转换路径的去留另行决策（见 ADR-0002 或后续 issue）。
- 业务基准示例见 [立项申请 BPMN](../examples/立项申请.bpmn)：审批结果可作为条件分支依据；会签任务完成与通过结论分开；打回后回到申请单并重新经过部所长审核。业务模型和编译器的后续验收应覆盖这些语义。
