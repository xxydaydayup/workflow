# 0001 - 引入业务模型层，编译下沉后端

官方 BPMN 设计器（bpmn-js）对业务管理员不友好；换用 react-flow 重画后仍未解决，因为不友好的根源在概念层——BPMN 术语（排他网关、assignee、formKey、监听器类名）和手写 EL 表达式直接暴露给用户——而非渲染层。决定：前端唯一编辑对象是与 BPMN 解耦的**业务模型**，前端以审批步骤、独立会签节点、条件分支及业务连线表达流程，后端负责编译为流程定义。立项申请表单及审批人员变量由后端约定，设计界面不维护表单 schema、审批人或 Camunda 配置。

## Considered Options

- 在现有 BPMN JSON 模型上继续加中文皮肤：被拒。适配层退化为格式转换，表达式与变量名仍需用户手工对齐。
- 前端编译（前端生成 BPMN XML）：被拒。业务模型 schema 演进会被 XML 兼容性锁死，camunda 命名空间知识泄漏进前端。

## Consequences

- 业务管理员只能使用当前产品提供的业务节点和路径语义，Camunda 全量能力不对其开放。
- 前端提交 `project_approval_json` 业务模型；业务模型编译为流程定义与发布流程定义是分开的操作。用户已确认现有 `/v1/bpmn/json2xml` 作为业务模型编译接口；前端直接传业务模型，不生成 BPMN XML。2026-10-23 实测编译返回有效 BPMN XML，审批分支、驳回回流和 ALL 会签结构通过检查。
- 表单 schema 与启动审批人员字段说明不进入设计器 DTO；后端按已发布流程返回启动字段说明，调用方启动实例时提交对应人员标识。会签作为独立节点类型表达，当前立项流程固定采用 ALL。
- 业务基准示例见 [立项申请 BPMN](../examples/立项申请.bpmn)：审批结果可作为条件分支依据；会签任务完成与通过结论分开；打回后回到申请单并重新经过部所长审核。业务模型和编译器的后续验收应覆盖这些语义。
