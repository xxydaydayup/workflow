# 可配置服务节点与通用流程设计器

Status: 可由智能体处理

## Problem Statement

当前 `/designer` 虽有节点库、画布和属性面板，但业务模型、初始流程、检查规则和发布入口都围绕立项审批固定。流程设计者无法独立设计其他业务流程，也不能表达服务调用步骤。前后端需要统一支持 `service` 节点，并区分在流程启动时提供服务地址的动态配置和在流程定义中固定服务地址的静态配置。

## Solution

将流程设计器改造成以通用业务模型为唯一编辑对象的轻量流程设计工具。当前阶段流程设计者可从节点库拖放节点、连接路径、编辑流程和已纳入范围的节点属性并执行结构检查，导出的业务 JSON 遵守前后端共同契约。服务节点提供名称和可选服务地址：服务地址留空表示动态地址，由启动流程的调用方提交；服务地址非空表示固定地址，随业务模型提交。后端继续负责把业务 JSON 编译为流程定义。编译、发布和运行时服务调用按后续需要逐步验收。

## User Stories

1. As a 流程设计者, I want to 创建不同业务用途的流程, so that 我可以复用设计器而不受固定立项审批模板限制。
2. As a 流程设计者, I want to 在节点库中查看可用业务节点, so that 我可以了解当前支持的流程步骤。
3. As a 流程设计者, I want to 将节点拖入画布, so that 我可以按业务需要组装流程。
4. As a 流程设计者, I want to 移动节点并创建、调整节点间的路径, so that 我可以表达实际的流程顺序和分支。
5. As a 流程设计者, I want to 编辑流程标识和流程名称, so that 生成的业务模型能被识别并显示给业务用户。
6. As a 流程设计者, I want to 为节点设置名称和适用的业务属性, so that 流程定义能清晰表达每个步骤的目的。
7. As a 流程设计者, I want to 在属性面板配置服务节点名称和可选服务地址, so that 我可以描述需要调用的业务服务。
8. As a 流程设计者, I want to 留空服务地址表示动态地址, so that 流程启动方可以在启动实例时决定调用地址。
9. As a 流程设计者, I want to 填写服务地址表示固定地址, so that 流程定义可以使用预先配置的服务端点。
10. As a 流程设计者, I want to 预览或导出符合约定的业务 JSON, so that 我可以检查生成的模型并提交给后端编译。
11. As a 流程设计者, I want to 检查流程结构和配置错误并跳转到对应元素, so that 我可以在编译前修复无效流程。
12. As a 流程设计者, I want to 查看后端编译和发布错误, so that 我可以根据权威校验反馈修正业务模型。
13. As a 流程发起方, I want to 在发起采用动态服务地址的流程时提供必需地址, so that 服务节点能够按本次业务选择的端点运行。
14. As a 流程发起方, I want to 对固定地址服务流程无需重复提供服务地址, so that 实例使用已发布流程中配置的端点。
15. As a 流程管理员, I want to 查看实例是否成功执行服务节点并获得有用的失败信息, so that 我可以诊断服务不可用或业务调用失败。
16. As a 流程后端开发者, I want to 将服务节点及其地址模式编译为 Camunda 流程定义, so that 流程引擎可以执行已发布的业务流程。
17. As a 流程管理员, I want to 让后端限制动态服务地址可访问的主机和网络范围, so that 流程发起输入不能触发对未授权网络目标的请求。
18. As a 流程设计者, I want to 保留流程节点标识和画布坐标, so that 节点重命名与移动不会破坏路径引用且 JSON 能重现设计布局。
19. As a 流程设计者, I want to 在会签节点选择模板固定模式或发起时动态选择, so that 单个模板可以按流程配置或业务实例传入控制审批方式。
20. As a 流程发起方, I want to 为动态会签选择 `ALL`、`ANY`、`VOTE` 或后端后续公开的模式并按需提供通过比例, so that 发起请求遵守当前模板暴露的模式和字段规则。

## Implementation Decisions

- 以业务模型为前端唯一编辑对象，画布视图状态通过显式适配生成业务 JSON；业务模型不暴露 BPMN、Camunda XML 或引擎实现配置。
- 通用流程至少支持开始、审批、条件、会签、服务和结束等已定义业务节点；节点添加、移动、连线、选中、属性编辑和模型导出不依赖立项专属节点 ID 或固定拓扑。业务模型顶层保留 `processId`、`processName`、`nodes`、`flows`。
- 服务节点类型为 `service`，必填 `id`、`name`、`x`、`y`；可选 `serviceName` 与 `serviceUrl`。固定服务样例使用 `serviceName` 描述业务服务名、`serviceUrl` 保存配置的地址；动态服务样例省略地址。示例中 `serviceName` 仅用于固定服务场景，不在未确认时强制动态服务同时提供它。
- `serviceUrl` 缺失或为空表示动态地址；非空表示固定地址。DTO 不添加未经前后端约定的 URL 模式字段，不改写现有 `flows` 的 `source`、`target`、`branch` 结构。
- 会签节点支持可选 `approveMode` 和 `passRate`。`approveMode` 是 `nodes[]` 中会签节点的业务模型属性，例如 `{"id":"managers","type":"countersign","approveMode":"ALL"}`；填写后作为节点配置交给编译接口。当前 `/bpmn/spec` 列出的值为 `ALL`、`ANY`、`VOTE`，其他值会被当前编译器拒绝。
- 后端业务模型 JSON 约定会持续演进，新增节点类型及其属性时以当时发布的 `/bpmn/spec` 为准。字段定义中的 `allowed` 是该字段可接受的值列表，不是额外的 JSON 属性或启动参数。将来若后端增加专门表示“发起时动态选择”的 `approveMode` 值，其具体字面值和行为由更新后的契约给出；前端不得预造该值。
- 模板未固化具体 `approveMode` 时，发起实例才可通过独立运行时变量 `{节点id}_approveMode` 指定，例如节点 ID 为 `managers` 时变量名是 `managers_approveMode`；这是启动请求 `variables` 对象中的键，不是业务模型节点字段。未提供时当前后端缺省 `ALL`。若未来选用后端定义的动态模式值，实例也按同一变量名传入。
- `passRate` 为字符串形式的通过比例，数值范围为 `(0, 1]`。模板中 `approveMode=VOTE` 时必须同时配置 `passRate`；模板未提供 `passRate` 时，按 `{节点id}_passRate` 在实例发起时提交。启动时动态 `approveMode` 与 `passRate` 的组合校验和后端变量元数据应由契约确认，前端不推断未约定的模式规则。
- 动态模式所需的启动变量必须由编译/模板元数据明确公开给流程发起方，并接受实际实例启动时的地址输入；固定模式无需为地址创建启动变量。具体变量名、格式、必填元数据、地址校验规则及错误结构须由前后端对齐。
- 编译接口继续接收业务 JSON 并由后端返回流程定义 XML；前端不生成或编辑 BPMN XML。编译、发布及运行时验证不属于当前聚焦的设计器交付，可后续按需完善。
- `branch: "pass" | "reject"` 可标记在 `approval`、`countersign`、`service` 的出边，也可用于 `condition` 的出边。条件节点出边使用 `branch` 时，条件节点须恰有一个直接审批、会签或服务上游；否则须用 `conditionExpression` 表达条件。属性面板允许编辑可选 `conditionExpression`，它优先于 branch 推导条件。打回目标由 reject 连线终点决定。设计器通用检查不得强制所有流程包含立项申请填写步骤、固定审批人员或立项专属回流结构。
- 当前设计器交付范围提供通用节点、当前已采用的节点属性、会签比例、服务地址和 `pass`/`reject` 路径，并生成可预览/下载的业务 JSON。后端约定中持续新增的可选节点属性，只有纳入产品范围并实现对应编辑/校验后才会进入设计器；不以现阶段 UI 字段列表代表后端契约的永久全集。发布、启动与 worker 运行验收留待后续。
- 端到端验收从服务节点的编辑配置贯穿业务 JSON 编译、Camunda 部署、实例启动、调用结果及失败反馈；接口隔离的模型映射检查可作为辅助，后端编译和引擎行为须有真实集成验证。
- 服务调用的 HTTP 方法、请求/响应映射、鉴权、超时、重试、结果变量和错误分支未在现有契约中定义；不能把这些能力隐含进本次服务 DTO。进入实现前应根据现有后端服务任务能力确定最小可运行约定，无法覆盖的内容记录为后续扩展。
- 动态地址属于运行时外部目标，后端必须实施可访问目标约束和重定向校验；前端校验只能提供即时反馈，不能替代后端安全边界。
- 设计器的流程标识、名称、初始模型、节点属性、结构检查和发布元数据应由当前流程编辑内容驱动；不得把立项业务 JSON 或其固定变量规则冒充通用默认值。

## Testing Decisions

- 验证以用户可观察行为和当前阶段的业务 JSON 契约为准；编译结果、部署版本、启动变量和服务调用运行结果在后续接入相应功能时验收。
- 当前设计器阶段以可观察的浏览器操作为主要验收：添加、移动、连接节点，编辑适用属性、检查流程并预览/下载符合 `/bpmn/spec` 的 JSON。编译、部署和运行集成属于后续范围。
- 重点覆盖空白/缺失地址判定为动态、非空地址判定为固定、动态地址缺失被拦截、固定地址不会要求发起方重复输入、节点名称/坐标和 flows 往返保持一致，以及不符合结构的模型在前端或后端返回可定位错误。
- 动态地址不可访问未授权主机、私有或本机目标以及经重定向转向受限目标的验证必须在后端执行环境完成；以拒绝结果和无目标请求作为安全验收证据。
- 后续接入编译、发布和运行时，再以真实服务调用、变量和结果作为集成验收证据；在此之前报告实际完成的浏览器与模型检查，不宣称端到端完成。
- 按仓库功能验证策略，默认运行应用并实际操作相关用户路径；不得新增或修改测试文件，除非用户在具体实现任务中明确要求。已有测试仅在能直接验证本次行为且合适时选择性运行。

## Out of Scope

- 在前端编辑或生成 Camunda BPMN XML。
- 由服务节点自动设计 HTTP 方法、请求体模板、响应解析、变量映射、认证凭据、重试、超时或补偿语义。
- 在浏览器中直接发起服务节点请求；服务节点由后端运行流程实例时执行。
- 立项专属表单 schema 编辑、审批人员配置、超出动态 `approveMode`/`passRate` 契约的会签业务规则变更，或改造监控业务。
- 在未约定服务参数 schema 与变量命名契约前，擅自定义业务服务的请求/响应数据结构。
- 以任何形式允许流程发起者绕过后端服务地址访问策略。
- 当前设计器阶段从画布页面触发编译、任务模板发布或实例发起；后续可按独立需求接入。

## Further Notes

- 服务节点验收样例以用户提供的“服务调用”业务模型为准：start → approval → service → condition，condition 的 pass 指向 end，reject 返回 approval。固定模式在 service 节点提供 `serviceName: "库存服务"` 和 `serviceUrl: "http://127.0.0.1:8080/api/stock/check"`；动态模式省略 `serviceUrl`。示例中的回环结构证明 reject 目标由连线配置，设计器与检查逻辑不得假定拒绝一定结束或一定回到固定申请节点。
- 样例固定 URL 使用本机回环地址，只作为字段结构示例，不能作为生产部署默认目标或后端可访问策略；安全集成验收应使用隔离的授权测试服务。
- 当前领域文件定义业务模型/流程定义/编译以及条件分支/打回等术语；服务节点及动态服务地址语义是新增概念，实施时应与后端补齐并对齐领域词汇和业务模型契约。
- 端到端验收回答已明确为必需，但后端可运行环境、服务模拟目标和服务节点执行契约尚未在仓库中找到，实施任务开始前需确认这些集成前提。
