# 07: 按启动说明发起审批实例

Type: task
Blocked by: 06: 编译并发布立项审批流程
Status: 前端已实现；独立模板已验收；正式业务表单待业务系统接入

**What to build:** 让调用方按已发布流程返回的启动字段说明发起立项审批实例。发起界面使用系统固定的立项申请表单，并只在运行时收集流程要求的审批人员标识；流程设计者不需要预先配置审批人或维护启动人员集合。

- [x] `/start-approval` 按已发布模板动态呈现必填启动人员字段，不硬编码变量名；兼容未提供 `source` 的历史字段。
- [x] 只提交 `source=start` 字段；`complete` / `engine` 字段不进入启动变量。旧字段缺少来源时按 `start` 兼容。
- [x] 页面按模板 `required` 校验字段；String 按单个人员标识提交，Array 按换行分割的人员标识数组提交。人员目录有效性无法由当前 API 验证；后端真实负向启动也接受缺项，因此不得声称后端强制校验。
- [x] 业务表单数据以业务系统提供的 JSON 对象与审批人员变量合并；JSON 与审批字段重名时阻止提交，避免覆盖。流程设计不定义表单字段。
- [x] 成功后展示业务键、流程实例/定义标识和状态；启动失败时显示后端错误并保留输入。
- [x] 独立真实启动验证单人及 Array 会签字段均被接受，实例返回 HTTP 201 / RUNNING；本地校验覆盖缺字段、空集合、重复人员、无效 JSON 与业务/流程变量重名。

## 2026-10-23 实现与验证记录

- 新增 `/start-approval` 页面，启动时读取共享模板 `project-approval` 当前版本、可发起状态及启动字段说明。页面只按 `source=start` 收集变量，不把 `complete` 或 `engine` 来源发送到 start API。
- 启动请求把业务系统提供的 JSON 表单值与审批人员变量合并，并生成租户内唯一业务键。业务表单字段定义仍归业务系统；本地输入区是集成契约演示，不表示流程设计器拥有表单 schema。
- 真实后端查询确认 `project-approval` v5 提供 `apply_assignee`、`minister_assignee` 两个 String 和 `managers_approverList` Array，三者均为 `source=start` 且 `required=true`。
- 真实启动返回 HTTP 201、状态 RUNNING；任务树返回当前节点为立项审批单，处理人为测试标识 `qa-starter`。缺少会签字段的负向真实调用也返回 HTTP 201，因此字段必填由 UI 执行，后端此处未验证人员目录有效性。
- 40 项 Vitest、typecheck、lint、build 通过；浏览器在 Vite 预览端口确认启动页呈现业务 JSON 输入和 3 个动态审批字段，空值提交由本地校验拦截。
- 剩余边界：业务系统需把固定立项表单值接入 JSON 输入；当前仓库没有业务表单 schema 或人员目录服务，无法验证人员 ID 在组织目录中存在。真实启动的两条业务记录回查状态均为 FAILED；引擎结束后业务 API 未能删除这些历史记录。用于验证的独立 taskKey 模板已按接口删除，未影响共享模板。
