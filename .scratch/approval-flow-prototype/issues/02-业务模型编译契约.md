# 02 - 业务模型编译契约（垂直切片：硬编码 JSON → 部署成功）

## 目标

前端零改动，验证最大技术风险点——后端编译器。用一个硬编码的业务模型 JSON，走通「校验 → 编译 BPMN → 部署 Camunda → 发起 → 审批 → 打回重提」全链路。编译通过并跑通打回，业务模型架构才算立住。

前置决策见 [ADR-0001](../../../docs/adr/0001-approval-model-and-backend-compilation.md) 与 [GLOSSARY](../../../GLOSSARY.md)。

## 业务模型 JSON（请假审批，验收主场景）

```json
{
  "schemaVersion": "1",
  "process": {
    "name": "请假审批",
    "code": "leave_approval"
  },
  "rejectBehavior": "returnToStart",
  "form": {
    "fields": [
      {
        "id": "leaveType",
        "label": "请假类型",
        "type": "enum",
        "required": true,
        "options": [
          { "value": "personal", "label": "事假" },
          { "value": "annual", "label": "年假" },
          { "value": "sick", "label": "病假" }
        ]
      },
      { "id": "startDate", "label": "开始日期", "type": "date", "required": true },
      { "id": "endDate", "label": "结束日期", "type": "date", "required": true },
      { "id": "leaveDays", "label": "请假天数", "type": "number", "required": true },
      { "id": "reason", "label": "事由", "type": "text", "required": false }
    ]
  },
  "flow": {
    "nodes": [
      { "id": "start_1", "type": "start" },
      {
        "id": "approve_1",
        "type": "approval",
        "name": "主管审批",
        "approver": { "mode": "member", "members": ["张伟"] },
        "method": "single"
      },
      { "id": "branch_1", "type": "condition", "name": "天数判断" },
      {
        "id": "approve_2",
        "type": "approval",
        "name": "HR 审批",
        "approver": { "mode": "member", "members": ["李娜", "王芳"] },
        "method": "countersign"
      },
      { "id": "cc_1", "type": "cc", "name": "抄送行政", "receivers": ["赵敏"] },
      { "id": "end_1", "type": "end" }
    ],
    "edges": [
      { "id": "e1", "source": "start_1", "target": "approve_1" },
      { "id": "e2", "source": "approve_1", "target": "branch_1" },
      {
        "id": "e3",
        "source": "branch_1",
        "target": "approve_2",
        "conditions": [{ "field": "leaveDays", "operator": ">", "value": 3 }]
      },
      { "id": "e4", "source": "branch_1", "target": "cc_1", "isDefault": true },
      { "id": "e5", "source": "approve_2", "target": "cc_1" },
      { "id": "e6", "source": "cc_1", "target": "end_1" }
    ]
  }
}
```

语义要点：

- `code` 是唯一英文标识（用户起的中文名由前端自动转写或让用户选），业务用户全程不接触。
- `form.fields` 的 `id` 是流程变量名，由系统生成，条件分支的 `conditions[].field` 只能引用它——**变量唯一来源**。
- `approver.mode`：`member`（手输人名）/ `starterSelect`（发起人自选）第一版实现；`leader`、`role` 为预留枚举，等组织架构 API。
- `method`：`single`（单人）/ `countersign`（会签）/ `orsign`（或签）。
- `rejectBehavior: returnToStart`：打回到发起人，重新提交后**回到打回它的节点**。

## 后端编译规则（业务模型 → BPMN XML）

| 业务模型                          | 编译为                                                                                                                                        | 说明                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `process.code`                    | `<process id isExecutable="true">`                                                                                                            |                                                                                        |
| `process.name`                    | process name                                                                                                                                  |                                                                                        |
| `start` 节点                      | `<startEvent camunda:initiator="initiator">`                                                                                                  |                                                                                        |
| （编译器自动插入）                | 「修改申请」userTask，`id=modify_apply_task`，`assignee=${initiator}`，插在 start 之后                                                        | 打回的落点；正常发起时由后端自动 complete，发起人无感                                  |
| `approval` + member 单人          | `<userTask camunda:assignee="张伟">`                                                                                                          |                                                                                        |
| `approval` + member 多人 + single | `camunda:candidateUsers="李娜, 王芳"`                                                                                                         | 任一人认领处理                                                                         |
| `approval` + countersign          | 并行多实例：`camunda:collection`（名单数组变量）、`camunda:elementVariable="approver"`、完成条件 `${nrOfCompletedInstances == nrOfInstances}` |                                                                                        |
| `approval` + orsign               | 同会签，完成条件 `${nrOfCompletedInstances >= 1}`                                                                                             |                                                                                        |
| `approval` + starterSelect        | `camunda:assignee="${starterSelected_approve_1}"`                                                                                             | 启动时由发起人传入同名变量                                                             |
| `condition` 节点                  | `<exclusiveGateway>`                                                                                                                          |                                                                                        |
| 带 `conditions` 的边              | `<sequenceFlow><conditionExpression xsi:type="tFormalExpression">${leaveDays > 3}</conditionExpression>`                                      | 结构化条件编译为 EL；enum 用 `${leaveType == "personal"}`；多条件 AND 用 `&&` 连接     |
| `isDefault` 边                    | 无条件的顺序流                                                                                                                                | 排他网关默认流向                                                                       |
| `cc` 节点                         | `<serviceTask>` 非阻塞通知                                                                                                                    | 实现方式后端定（表达式/委托 Bean 调通知服务）；业务模型不关心                          |
| `end` 节点                        | `<endEvent>`                                                                                                                                  |                                                                                        |
| `form`                            | **不编译进 BPMN**                                                                                                                             | 表单定义存任务模板元数据，前端渲染，字段值走启动变量；formKey/Generated Forms 全部消失 |

工程要求：

- XML 用 Camunda Model API（`org.camunda.bpm.model`）构建对象树后序列化，禁止字符串拼接——避免重蹈 `<incoming>` 合并 bug（见 [01-后端部署增强导致XML解析失败](01-后端部署增强导致XML解析失败.md)）。
- process 补 `camunda:historyTimeToLive`。
- 生成 BPMN DI（图形坐标），Cockpit 要能看到流程图；坐标可先自动布局，前端坐标映射后续做。
- 新接口建议：`POST /v1/task/approval-models/deploy`，入参业务模型 JSON + 元数据，一步完成校验 → 编译 → 部署 → 落库任务模板，返回 `{ taskKey, deploymentId, processDefinitionId, bpmnXml }`。旧 `json2xml` 路径废弃，其 bug 不修。

## 打回与重新提交（运行时语义）

1. **发起**：start 接口带表单变量启动 → 后端立即自动 complete `modify_apply_task` → 流程停在第一个审批节点。
2. **同意**：complete → 流转（网关按变量选边）。
3. **打回**：refuse 接口 → `runtimeService.createChangeActivityStateBuilder().moveActivityIdTo("<当前节点>", "modify_apply_task")`，并写变量 `returnedFrom=<当前节点>` → 发起人待办出现「修改申请」。注意：从会签（多实例）打回需先查 activity instance tree，用 `moveActivityInstanceIdTo`；跳转会终止该多实例全部子任务，即任一审批人打回整组取消。
4. **重新提交**：complete `modify_apply_task`（新表单值作为变量）→ 后端按 `returnedFrom` 跳回打回来源节点。

## 验证步骤

```bash
# 1. 部署（curl / Postman 发上面的 JSON）
curl -X POST http://<backend>/v1/task/approval-models/deploy \
  -H 'Content-Type: application/json' \
  -d @approval-model.json

# 2. 发起 5 天事假（应走主管 → HR 会签）
curl -X POST http://<backend>/v1/task/instances/start \
  -H 'Content-Type: application/json' \
  -d '{ "taskKey": "leave_approval", "businessKey": "L001",
        "variables": { "leaveType": "personal", "leaveDays": 5,
                       "startDate": "2026-10-21", "endDate": "2026-10-25", "reason": "test" } }'

# 3. 发起 2 天事假（应走主管 → 直接抄送 → 结束）——变量改为 leaveDays: 2
```

逐项检查：

1. Cockpit 里流程定义存在、图形正确、可执行。
2. 张伟有待办；同意后 leaveDays=5 时李娜、王芳各有任务（会签），leaveDays=2 时直接到抄送后结束。
3. 张伟打回 → 发起人出现「修改申请」→ 改 leaveDays=1 重新提交 → 流程回到张伟的待办。

验收标准：全链路无手写 EL 表达式、无 BPMN 术语；打回后回到打回节点而非从头重走。
