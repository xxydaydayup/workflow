## 当前范围：验证立项业务模型编译契约

## 目标

使用当前确认的立项审批业务模型验证后端编译器：按 [project_approval_json 契约](../../../docs/examples/立项申请/project_approval_json.md)提交流程 JSON，取得有效 BPMN XML，并确认通过/驳回、回到申请填写节点及 ALL 会签等路径语义。转换成功后再另行评估发布与运行时的端到端验证。

## 已确认的前端契约

- 节点类型为 `start`、`approval`、`condition`、`countersign`、`end`；会签节点为 `countersign`，`approveMode: ALL` 固定。
- 连线使用 `source`、`target`；从条件节点发出的审批结果连线使用 `branch: pass | reject`。审批人和表单 schema 不在设计模型中。
- 完整模型中的 reject 路径目标用于识别申请填写节点。基准 JSON 和流程语义见契约文档与 [立项审批 BPMN](../../../docs/examples/立项申请.bpmn)。

## Superseded original scope: leave-approval end-to-end verification

## 目标

前端零改动，验证最大技术风险点——后端编译器。用一个硬编码的业务模型 JSON，走通「校验 → 编译 BPMN → 部署 Camunda → 发起 → 审批 → 打回重提」全链路。编译通过并跑通打回，业务模型架构才算立住。

前置决策见 [ADR-0001](../../../docs/adr/0001-approval-model-and-backend-compilation.md) 与 [GLOSSARY](../../../GLOSSARY.md)。

业务语义以[立项申请 BPMN 业务基准](../../../docs/examples/立项申请.bpmn)为准。本文件中的请假流程是原型草案；模型契约须兼容审批结论驱动条件分支、会签完成条件与通过结论分离，以及打回后回到申请单再走后续审核。

## 业务模型 JSON（请假审批，验收主场景）

```json
{
  "schemaVersion": "1",
  "process": {
    "name": "请假审批",
    "code": "leave_approval"
  },
  "rejectBehavior": "returnToInitiator",
  "form": {
    "fields": [
      {
        "id": "leaveType",
        "label": "请假类型",
        "type": "enum",
        "required": true,
        "options": [
          { "value": "personal", "label": "事假" },
          { "value": "annual", "label": "年假" },
          { "value": "sick", "label": "病假" }
        ]
      },
      { "id": "startDate", "label": "开始日期", "type": "date", "required": true },
      { "id": "endDate", "label": "结束日期", "type": "date", "required": true },
      { "id": "leaveDays", "label": "请假天数", "type": "number", "required": true },
      { "id": "reason", "label": "事由", "type": "text", "required": false }
    ]
  },
  "flow": {
    "nodes": [
      { "id": "start_1", "type": "start" },
      {
        "id": "approve_1",
        "type": "approval",
        "name": "主管审批",
        "approver": { "mode": "member", "members": ["张伟"] },
        "method": "single"
      },
      { "id": "branch_1", "type": "condition", "name": "天数判断" },
      {
        "id": "approve_2",
        "type": "approval",
        "name": "HR 审批",
        "approver": { "mode": "member", "members": ["李娜", "王芳"] },
        "method": "countersign"
      },
      { "id": "cc_1", "type": "cc", "name": "抄送行政", "receivers": ["赵敏"] },
      { "id": "end_1", "type": "end" }
    ],
    "edges": [
      { "id": "e1", "source": "start_1", "target": "approve_1" },
      { "id": "e2", "source": "approve_1", "target": "branch_1" },
      {
        "id": "e3",
        "source": "branch_1",
        "target": "approve_2",
        "conditions": [{ "field": "leaveDays", "operator": ">", "value": 3 }]
      },
      { "id": "e4", "source": "branch_1", "target": "cc_1", "isDefault": true },
      { "id": "e5", "source": "approve_2", "target": "cc_1" },
      { "id": "e6", "source": "cc_1", "target": "end_1" }
    ]
  }
}
```

语义要点：

- `code` 是唯一英文标识（用户起的中文名由前端自动转写或让用户选），业务用户全程不接触。
- `form.fields` 的 `id` 是表单变量名，由系统生成。条件分支还可能引用审批结论等流程变量，不能假设表单字段是唯一变量来源。
- `approver.mode`：`member`（手输人名）/ `starterSelect`（发起人自选）第一版实现；`leader`、`role` 为预留枚举，等组织架构 API。人名不做存在性校验，用户填谁就是谁：引擎按字符串路由待办，填错的代价是静默死单（无报错、待办无人可见），用 reassign 接口兜底；组织架构 API 就绪后升级为选人引用并校验。
- `method`：`single`（单人）/ `countersign`（会签）/ `orsign`（或签）。**约束：`single` 必须恰好 1 个成员；≥2 个成员必须显式选 `countersign` 或 `orsign`**。不引入 candidateUsers——「任一人认领」藏着业务看不见的认领中间态，与或签语义撞车。
- 打回到申请人修改；重新提交后的回流路径由业务流程决定。业务基准两处打回均回到立项申请单，再次经过部所长审核，不要求回到触发打回的节点。

## 后端编译规则（业务模型 → BPMN XML）

| 业务模型                   | 编译为                                                                                                   | 说明                                                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `process.code`             | `<process id isExecutable="true">`                                                                       |                                                                                                                  |
| `process.name`             | process name                                                                                             |                                                                                                                  |
| `start` 节点               | `<startEvent camunda:initiator="initiator">`                                                             |                                                                                                                  |
| （编译器自动插入）         | 「修改申请」userTask，`id=modify_apply_task`，`assignee=${initiator}`，插在 start 之后                   | 打回的落点；正常发起时由后端自动 complete，发起人无感                                                            |
| `approval` + member 单人   | `<userTask camunda:assignee="张伟">`                                                                     | single 恰好 1 个成员；不使用 candidateUsers（见语义要点 method 约束）                                            |
| `approval` + countersign   | 并行多人任务；完成条件由该流程的会签规则确定                                                             | 不能默认要求所有人完成；业务基准使用 `${decided}`，另以 `${passed}` 表达会签结论                                 |
| `approval` + orsign        | 并行多人任务；按或签规则确定节点完成和整体结论                                                           | 完成条件及剩余任务处理应由业务规则明确                                                                           |
| `approval` + starterSelect | `camunda:assignee="${starterSelected_approve_1}"`                                                        | 启动时由发起人传入同名变量                                                                                       |
| `condition` 节点           | `<exclusiveGateway>`                                                                                     |                                                                                                                  |
| 带 `conditions` 的边       | `<sequenceFlow><conditionExpression xsi:type="tFormalExpression">${leaveDays > 3}</conditionExpression>` | 结构化条件可引用表单字段或审批结论；业务基准用 `${approved}` / `${!approved}` 和 `${passed}` / `${!passed}` 分流 |
| `isDefault` 边             | 若业务模型定义默认边，则该边无条件且网关元素设置 `default` 属性                                          | 业务基准以互补的明确条件覆盖两种结果，没有单独默认边；需明确验证条件覆盖范围                                     |
| `cc` 节点                  | `<serviceTask>` 非阻塞通知                                                                               | 实现方式后端定（表达式/委托 Bean 调通知服务）；业务模型不关心                                                    |
| `end` 节点                 | `<endEvent>`                                                                                             |                                                                                                                  |
| `form`                     | **不编译进 BPMN**                                                                                        | 表单定义存任务模板元数据，前端渲染，字段值走启动变量；formKey/Generated Forms 全部消失                           |

## 变量类型映射与注入

| form 字段类型 | 流程变量 TypedValue | 说明                                                   |
| ------------- | ------------------- | ------------------------------------------------------ |
| `number`      | Long                | 数值比较（如 `leaveDays > 3`）必须走数值，不能是字符串 |
| `text`        | String              |                                                        |
| `enum`        | String              | 取选项 `value`，条件编译为 `==` 字符串比较             |
| `date`        | String（ISO 日期）  | 第一版不参与条件比较                                   |

全部按 String 传入会导致 `leaveDays > 3` 退化为字符串比较或 EL 异常，start 接口必须按上表落 TypedValue。

系统注入变量（非表单来源）：

- `approverList_<nodeId>`：member 静态名单数组，由 start 接口按节点注入，会签/或签的 `camunda:collection` 引用它。
- `approved` / `passed`：审批结果变量，由审批任务处理逻辑产生并用于条件流转；其具体写入时机和多人审批投票策略需确认。
- `starterSelected_<nodeId>`：starterSelect 模式下发起人传入的选定人。
- `returnedFrom`：打回来源节点 id，refuse 时写入。

工程要求：

- XML 用 Camunda Model API（`org.camunda.bpm.model`）构建对象树后序列化，禁止字符串拼接——避免重蹈 `<incoming>` 合并 bug（见 [01-后端部署增强导致XML解析失败](01-后端部署增强导致XML解析失败.md)）。
- process 补 `camunda:historyTimeToLive`。
- 生成 BPMN DI（图形坐标），Cockpit 要能看到流程图；坐标可先自动布局，前端坐标映射后续做。
- 新接口建议：`POST /v1/task/approval-models/deploy`，入参业务模型 JSON + 元数据，一步完成校验 → 编译 → 部署 → 落库任务模板，返回 `{ taskKey, deploymentId, processDefinitionId, bpmnXml }`。旧 `json2xml` 路径废弃，其 bug 不修。

## 打回与重新提交（运行时语义）

1. **发起**：后端先 `identityService.setAuthenticatedUserId(发起人)`——不设则 `${initiator}` 为 null，`modify_apply_task` 无人可见。start 接口带表单变量启动 → 后端立即自动 complete `modify_apply_task` → 流程停在第一个审批节点。
2. **同意**：complete → 流转（网关按变量选边）。
3. **打回**：refuse 接口 → `runtimeService.createChangeActivityStateBuilder().moveActivityIdTo("<当前节点>", "modify_apply_task")`，并写变量 `returnedFrom=<当前节点>` → 发起人待办出现「修改申请」。注意：从会签（多实例）打回需先查 activity instance tree，用 `moveActivityInstanceIdTo`；跳转会终止该多实例全部子任务，即任一审批人打回整组取消。
4. **重新提交**：修改表单后按流程定义继续。业务基准回到立项申请单后再次经过部所长审核，所以不能把运行时跳回“打回来源节点”设为通用语义；具体编译与运行时机制待与业务基准对齐。
