## Decisions-so-far

- 已创建立项审批实现 tickets：issues/03 对齐业务模型契约 → 04 三栏流程设计器 → 05 路径检查；06 编译发布依赖既有 issue 02 与 05；07 启动实例依赖 06。每项任务单独记录在 issues/03–07。
- React Flow 编辑模型与后端 `ProcessDefinitionDTO` 通过显式适配转换，不能互相当成同一结构。证据：本地 issue `01-可视化原型.md` 及分支 `codex/approval-flow-prototype`。
- 前端唯一编辑对象是与 BPMN 解耦的业务模型；业务模型到流程定义的编译在后端完成；表达力收缩为枚举化审批模式。见 [ADR-0001](../../docs/adr/0001-approval-model-and-backend-compilation.md)。
- 第一版节点：`start`、`approval`、`condition`、`countersign`、`end`；会签为独立 `countersign` 类型，固定 `approveMode: ALL`。表单固定由业务系统提供，审批人不在设计期配置。
- 打回语义以业务基准规定的路径为准：审批或会签不通过都回到申请填写步骤，重新提交后再次经过后续审批；申请填写节点依据拓扑识别，不添加用途字段或固定节点 ID 依赖。
- 审批人由后端按已发布流程返回启动字段描述，实例发起方传后端认可的人员标识；前端不绑定变量名或人名输入方案。
- 条件节点按审批结论分流，使用 `pass` / `reject` 两种业务路径；前端检查流程图结构，后端编译和发布校验为最终判断。
- 用户已确认现有 `/v1/bpmn/json2xml` 作为业务模型转换接口；前端直接发送 `project_approval_json`，转换和发布分开。2026-10-23 实测 HTTP 200，XML 可解析，节点、分支、回流及 ALL 会签语义验证通过。
- 实施切新分支进行；垂直切片先行——硬编码业务模型 JSON 验证后端编译器，见 issue `02-业务模型编译契约.md`。
- 监控页第一版不动。
- 请假审批是原型草案场景；后续讨论以业务基准中的立项申请流程校准流程语义。
